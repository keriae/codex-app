## Result and verification

The former Add buttons only changed a renderer-local `Set`, and the source-add menu did not perform an operation. The page now renders the server's actual catalog and installed state. Catalog entries from the recording are retained as disabled offline previews when inventory cannot be loaded. Installed sidebar entries and the Personal tab come from server state. Search uses names, descriptions, categories and developer names. Plugin and skill load failures are shown independently; old workspace responses are discarded.

Both Marketplace and Settings can enable/disable and uninstall installed plugins. Marketplace can install available plugins, view actual detail content, add a marketplace and enable/disable discovered skills through `skills/config/write`. The already-present Settings skill operations continue to work. Refresh failures after a successful operation are reported as refresh failures rather than pretending the mutation did not happen.

The Add dialog supports submit errors, progress, Escape, outside click, focus restoration and tab containment. Plugin read/install errors remain visible and installation state is refreshed from the backend. Returned connection links accept only HTTP(S) URLs without embedded credentials.

Catalog logos use editable CSS, text and open-source icon approximations. Installed application and plugin image assets are not distributed with the editable client.

## Final asynchronous state audit

A subsequent read-only audit exercised current renderer code with synthetic bridge promises and static React rendering. It compared the running import branch and prior-import time against original `fn` at offset **2006** in `import-settings-780d381a10e8.js`: running state comes from the native import context independently of earlier history, and the no-new branch explicitly consumes `latestSuccessfulImportAtMs`. The audit also followed the implemented native timeout/completion contract in [external-agent-import.md](external-agent-import.md).

Three reproducible edge cases were repaired in the renderer, each with a regression test:

- A completed operation no longer hides a different active attempt returned by native status. A terminal result remains protected against a stale status response for the same attempt.
- A trusted terminal result is retained if the original import caller's older timeout rejection reaches the renderer afterward. Completion callbacks remain exactly once.
- The empty/no-new view derives the previous successful import time from history entries with actual successes. Failed-only history and an unverified status timestamp cannot produce a successful-import date.

The audit separately verified that stop remains pending until native completion, timeout-then-late-completion restores the actual result, project configuration selection preserves selected chats, and partial review shows the actual success/failure counts. The pre-repair and post-repair synthetic observations are ignored at `reverse/raw/checks/current/settings/import-readonly-audit-results.json` and `import-readonly-audit-fixed-results.json`. The targeted four renderer files pass **28 tests** and Web typechecking passes. The full repository suite and final-package acceptance are recorded separately in [source-validation-current.md](source-validation-current.md); this targeted audit does not supply their total or claim complete visual parity.

This work does not mark Settings or Marketplace fully identical to the production application. Remote host management, marketplace removal/upgrade, plugin sharing, in-app OAuth orchestration, plugin starter prompts, complete skill editors and all local settings categories still have outstanding implementation or visual acceptance work. The new detail/Add views follow inspected source contracts but require continued pixel comparison against the production views when a usable reference is available.
